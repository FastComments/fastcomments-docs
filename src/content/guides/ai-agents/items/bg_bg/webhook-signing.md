Всеки агентски уебхук е подписан с HMAC-SHA256 с помощта на API секрета на вашия tenant. Използва се същата схема на подписване като за уебхуците за коментари на FastComments - ако вече сте ги интегрирали, агентските уебхуци използват същия signature header и същия процес на проверка.

### Защо се подписва

Без подпис атакуващ, който знае URL адреса на вашия уебхук, може да изпраща фалшиви събития, които изглеждат сякаш идват от FastComments. Подписването означава, че вашият endpoint може да провери, че всяко доставяне е автентично, преди да действа по него.

### Как работят подписите

За всяко доставяне:

1. Платформата намира API секрета за tenant + съответстващия домейн (вижте [Преглед на уебхуците](#webhooks-overview)).
2. Изпраща текущия Unix timestamp (в милисекунди) в header-а `X-FastComments-Timestamp`.
3. Изчислява `HMAC-SHA256(api_secret, "${timestamp}.${raw_request_body}")` (в стил Stripe) и изпраща резултата като `sha256=<hex>` в header-а `X-FastComments-Signature`.
4. Вашият endpoint прочита timestamp header-а, преизчислява HMAC върху `${timestamp}.${body}`, който е получил, сравнява със стойността `sha256=<hex>` в signature header-а и отхвърля несъответствията.

Подписаното тяло са **точните байтове**, които платформата е изпратила, с префикс `${timestamp}.` - вашият verifier трябва да използва суровото тяло на заявката, а не повторно сериализиран JSON низ (иначе подредбата на ключовете и интервалите биха се различавали).

### API секрет

Използва се същият API Secret като за [уебхуците за коментари](/guide-webhooks.html). Той е на (tenant, домейн) и се управлява в API настройките на вашия tenant. Ако смените секрета, трябва да разположите отново вашия verifier, за да прочете новата стойност преди следващото доставяне.

Когато платформата не намери **API секрет** за съответстващия домейн, доставянето не се извършва. Логът на уебхука записва неуспеха с причина "no API secret".

### Пример за проверка (Node.js)

[inline-code-attrs-start title = 'Пример за проверка на подписа на уебхук'; type='javascript' inline-code-attrs-end]
[inline-code-start]
import crypto from 'crypto';

function verifyAgentWebhook(rawBody, signatureHeader, timestampHeader, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(`${timestampHeader}.${rawBody}`)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader),
  );
}
[inline-code-end]

Използвайте `timingSafeEqual` вместо `===`, за да избегнете изтичане на подписа чрез timing-канали.

### Какво съдържа подписаното тяло

Пълният envelope плюс блока `data`, специфичен за събитието. Вижте [Полезни товари на уебхуците](#webhook-payloads).

### Препоръки

- **Проверявайте при всяко доставяне.** Ако вашият endpoint приема неподписани заявки, нямате гаранция за цялостност.
- **Отхвърляйте при несъответствие на подписа.** Върнете 401 или 403; не връщайте 200 OK при грешен подпис, иначе ще прикриете атаките в логовете си за доставяне.
- **Използвайте HTTPS.** Подписите защитават цялостността; TLS защитава поверителността (както вашия секрет, така и текста на коментарите в полезния товар).
- **Сменяйте секретите**, когато членове на екипа с достъп напускат, или по график.

### Защита от повторно изпращане

Самото подписване не предотвратява replay атаки - атакуващ, който е прихванало реално подписано доставяне, може да го изпрати отново. Защитата от replay е отговорност на вашия endpoint:

- Използвайте полето `occurredAt` от envelope-а и отхвърляйте доставяния, по-стари от, да речем, 5 минути.
- Използвайте `triggerId` или `approvalId` като ключ за дедупликация - ако вече сте го обработили, игнорирайте дубликата.
