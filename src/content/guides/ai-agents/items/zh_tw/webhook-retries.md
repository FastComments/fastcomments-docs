Agent webhook 在失敗時會自動重試。從 agent 的角度來看，傳送是**發後即忘（fire-and-forget）** - 傳送失敗不會阻擋 agent 執行，也不會回滾任何動作 - 並且由佇列 + cron 以非同步方式驅動重試。

### 佇列模型

每個事件會針對**每個符合的 webhook 各排入佇列一次**。因此，如果您有三個訂閱了某個 agent + 網域之 `trigger.succeeded` 的 webhook，平台會排入三次傳送；每次傳送都會獨立傳送與重試。某個 webhook 的失敗絕不會影響其他 webhook。

### 重試的條件

在以下情況會重試傳送：

- HTTP 請求**未完成**（DNS 失敗、連線被拒、逾時）。
- HTTP 回應代碼為任何非 2xx 狀態，且不在已設定的**免重試狀態代碼**清單中。

在以下情況**不會重試**傳送：

- 回應代碼為 `2xx`（成功）。
- 回應代碼在已設定的**免重試狀態代碼**清單中。預設此清單為空 - 任何非 2xx 都會重試。

### 設定免重試代碼

webhook 設定表單中有一個**免重試狀態代碼**欄位（可多值）。常見的項目：

- `410` - Gone。您的端點已永久搬移，或資源已不存在。重試只會浪費雙方的頻寬。
- `422` - Unprocessable Entity。您的端點理解了酬載但認為其無效。使用相同的酬載重試會得到相同的答案。
- `400` - Bad Request，基於同樣的道理。

在此新增一個代碼表示：當端點回傳該代碼時，將該傳送標記為最終失敗並停止重試。

### 重試排程

背景工作程序每隔幾秒執行一次，並處理任何下次嘗試時間已過的傳送。

每次失敗後，下次嘗試時間會以**線性退避（linear backoff）**往後推：等待時間以 `60 seconds * attempt count` 增長（因此第 1 次嘗試等待 1 分鐘，第 2 次嘗試等待 2 分鐘，依此類推）。

在 99 次失敗嘗試後（本地開發環境為 3 次），該傳送會被放棄並從佇列中移除。傳送日誌項目會持續保留，並在 [Webhook Delivery Logs](#webhook-logs) 頁面上保持可見，直到過期為止。

### 您這一端的等冪性

因為我們會重試，您的端點**必須是等冪的（idempotent）**。同一個 `triggerId`（或 `approvalId`）可能會送達多次。您的端點應該：

- 使用唯一鍵（觸發事件用 `triggerId`，核准事件用 `approvalId`）作為去重權杖（dedup token）。
- 優雅地接受重複的傳送（第二次回傳 200）。

非等冪的端點最終會重複處理某些傳送，特別是在暫時性中斷期間，此時某次逾時會在 30 秒後重試，但原始請求實際上已成功。

### 順序

傳送**並非嚴格排序**。`trigger.succeeded` 與下游的 `approval.requested`（來自同一次執行）可能以任一順序送達，如果其中一個重試而另一個沒有。您的端點不應假設因果順序。

如果您需要排序，請使用時間戳記 - 信封上的 `occurredAt`，加上資料區塊中的 trigger/approval `createdAt` - 在您這一端重建順序。

### 清理

傳送一旦成功或達到嘗試次數上限，就會立即從佇列中移除。平台不會在最終失敗的傳送留在佇列中；每次嘗試的持久記錄存放在 [Webhook Delivery Logs](#webhook-logs) 頁面。

### 重試失敗時該去哪裡查看

[Webhook Delivery Logs](#webhook-logs) 頁面是查看 webhook 為何失敗的地方。常見原因：

- **DNS 解析失敗** - URL 錯誤或網域已不存在。
- **TLS 錯誤** - 您端點的憑證無效或已過期。
- **連線被拒 / 逾時** - 您的端點當機了。
- **5xx 回應** - 您的端點在線但發生錯誤。回應主體（已截斷）會被記錄。
- **4xx 回應** - 您的端點拒絕了酬載。如果這是有意為之，請將該代碼加入**免重試狀態代碼**。

### 暫停不健康的 webhook

如果某個 webhook 持續失敗，最乾淨的解決方式是刪除它（或暫時清空其事件訂閱清單）。平台不會自動停用失敗的 webhook - 它們會持續重試，直到傳送被放棄為止。
