**테스트 런**(test run, **리플레이**라고도 함)은 실제 작업을 수행하지 않고 과거 댓글 창(window)에 대해 에이전트를 실행합니다. 라이브로 전환하기 전에 에이전트 동작을 미리 확인하는 가장 빠른 방법입니다.

에이전트 목록 페이지에서 각 에이전트 행의 **Test run** 버튼을 통해 접근할 수 있습니다.

### 수행 내용

플랫폼은 다음을 수행합니다:

1. 에이전트의 범위에 맞는 과거 댓글 샘플을 선택한 기간 내에서 선택합니다.
2. 각 댓글에 대해 해당 댓글이 방금 게시된 것처럼 에이전트를 엔드투엔드로 실행합니다 - 동일한 컨텍스트, 동일한 LLM 호출, 동일한 도구 선택, 동일한 근거 및 신뢰도 점수.
3. 모든 실행을 드라이런(dry-run)으로 기록하고, 해당 리플레이와 함께 그룹화되도록 태그를 지정하며 라이브 실행 뷰에서는 제외됩니다.
4. 에이전트의 판정을 댓글에 실제로 일어난 일과 **비교**합니다 - 나중에 승인되었는지, 스팸으로 표시되었는지, 삭제되었는지, 스팸 엔진에 의해 차단되었는지 등.

결과는 댓글별 diff입니다: "리플레이 에이전트는 이 댓글을 스팸으로 표시할 것이지만, 실제로는 승인되어 정상 상태입니다."

### 설정

테스트 런 페이지에는 단일 입력 항목이 있습니다:

- **평가할 과거 댓글 일수(Days of historical comments to evaluate)** - 1에서 90 사이의 숫자형 `days` 필드. 그보다 오래된 댓글은 대상이 되지 않습니다.

샘플 크기와 하드 캡은 **UI에 노출되지 않습니다** - 둘 다 플랜별로 적용되는 서버 측 기본값입니다. 페이지에는 정보성 필드가 표시됩니다:

- **기간 내 일치하는 댓글(Matching comments in window)** - 고려될 댓글 수.
- **이 기간에서 최대 N개의 댓글이 처리됩니다(Up to N comments from this window will be processed)** - 서버 측 캡을 반영한 유효 샘플 크기.
- **예상 비용(Estimated cost)** - 테넌트의 통화 기준.

### 속도 제한

각 사용자는 **24시간당 10회의 테스트 런**으로 제한됩니다(키 `replay-create:${requestedBy}`를 통해 속도 제한). 제한에 도달하면 버튼에 툴팁이 표시됩니다("You've reached 10 test runs in the last 24 hours.").

### 동시성

에이전트당 한 번에 하나의 리플레이만 활성화될 수 있습니다. 실행 중인 리플레이가 있을 때 두 번째 리플레이를 시작하면 실행 중인 리플레이로 리디렉션됩니다.

### 결과 읽기

리플레이가 완료되면 결과 페이지에 탭이 표시됩니다:

- **Deltas**(기본 활성) - 리플레이 에이전트의 판정이 실제와 다릅니다. (가장 흥미로운 경우 - "에이전트는 이 댓글을 스팸으로 표시했을 것이지만, 실제로는 승인되어 정상입니다".)
- **Matches** - 리플레이 에이전트의 판정이 실제로 일어난 일과 일치합니다. (안심되는 경우 - 에이전트가 실제와 일치합니다.)
- **No action** - 리플레이 에이전트가 아무 작업도 하지 않기로 결정했습니다. (때로는 올바른 답이고, 때로는 에이전트가 무언가를 놓친 경우입니다.)
- **All** - 분류와 관계없이 모든 결과.

각 탭의 각 댓글에 대해:

- **Prior outcome** - 실제로 일어난 일의 분류: **POSITIVE**, **NEGATIVE**, 또는 **INDETERMINATE**, **Evidence**와 함께 ("Comment marked deleted at {date}", "Engine: bayes" 등).
- **Replay agent would** - 에이전트가 선택한 작업.
- **Why** - 근거.
- **Confidence** - 백분율로 표시됩니다.

### 리플레이가 드라이런을 강제하는 이유

4개월 전에 삭제된 댓글에 대한 리플레이는 소급하여 삭제해서는 안 됩니다 - 이미 삭제되었기 때문입니다. 에이전트가 이제 승인하려는 댓글에 대한 리플레이는 댓글의 현재 상태를 변경해서는 안 됩니다. 리플레이는 미리보기 도구입니다. 드라이런을 강제하는 것이 어떤 과거 기간에 대해서도 안전하게 리플레이를 실행할 수 있게 만듭니다.

### 재현성

리플레이는 리플레이가 시작된 시점의 에이전트 구성을 고정합니다. 이후 에이전트에 대한 편집은 리플레이 결과에 영향을 주지 않습니다 - 결과 페이지는 *해당* 버전의 에이전트가 수행했을 작업의 기록으로 안정적으로 유지됩니다.

### 예산이 리플레이를 중단하는 경우

리플레이는 다음의 영향을 받습니다:

- 자체 **하드 캡**(리플레이 양식에서 설정).
- 에이전트의 일일 및 월간 **예산 캡**.
- 테넌트의 일일 및 월간 **예산 캡**.

먼저 도달한 항목이 특정 오류 코드와 함께 리플레이를 중단시킵니다. 중단 전에 생성된 댓글별 결과는 [Run History](#run-history)에 보존됩니다.

### 리플레이 실행 방식

리플레이는 동기식이 아닌 백그라운드에서 실행됩니다. "Start test run"을 클릭하면 리플레이가 대기열에 들어가고 워커가 이를 가져갑니다. 긴 리플레이는 몇 분에 걸칠 수 있습니다. 결과 페이지는 진행 상황(처리된 수, 현재까지 지출)을 폴링하며 표시합니다.

워커가 리플레이 도중 죽으면 플랫폼이 자동으로 리플레이를 다시 대기열에 넣어 다음 패스에서 재개합니다. 일시적인 장애로 리플레이가 고아가 되는 일은 없습니다.

### 리플레이가 하지 않는 것

- **[트리거 지연](#trigger-deferred-delay)을 따르지 않습니다.** 리플레이는 30분 후가 아니라 즉시 실행됩니다.
- **메모리에 쓰지 않습니다.** 리플레이 에이전트는 로직상 일반적으로 저장하더라도 메모리 노트를 저장하지 않습니다.
- **웹훅을 발생시키지 않습니다.** 리플레이에서 생성된 트리거는 `trigger.succeeded` / `trigger.failed` 웹훅 이벤트를 생성하지 않습니다.
- **이미 리플레이된 댓글을 제외하지 않습니다.** 동일한 기간에 대해 두 번째 리플레이를 실행하면 동일한 댓글을 다시 처리합니다.
