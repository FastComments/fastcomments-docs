Каждый webhook агента подписывается с помощью HMAC-SHA256 с использованием API-секрета вашего тенанта. Та же схема подписывания используется для webhook'ов комментариев FastComments — если вы уже интегрировали их, webhook'и агентов используют тот же заголовок подписи и процесс верификации.

### Зачем нужно подписывание

Без подписи злоумышленник, знающий URL вашего webhook'а, мог бы отправлять поддельные события, выглядящие так, будто они пришли от FastComments. Подписывание позволяет вашему эндпоинту проверять подлинность каждой доставки перед её обработкой.

### Как работают подписи

Для каждой доставки:

1. Платформа ищет API-секрет для тенанта + совпавшего домена (см. [Обзор Webhooks](#webhooks-overview)).
2. Она отправляет текущую Unix-метку времени (в миллисекундах) в заголовке `X-FastComments-Timestamp`.
3. Она вычисляет `HMAC-SHA256(api_secret, "${timestamp}.${raw_request_body}")` (в стиле Stripe) и отправляет результат как `sha256=<hex>` в заголовке `X-FastComments-Signature`.
4. Ваш эндпоинт читает заголовок с меткой времени, заново вычисляет HMAC над полученными `${timestamp}.${body}` и сравнивает со значением `sha256=<hex>` в заголовке подписи, отклоняя несовпадения.

Подписанное тело — это **точные байты**, отправленные платформой, с префиксом `${timestamp}.` — ваш верификатор должен использовать необработанное тело запроса, а не повторно сериализованную JSON-строку (иначе порядок ключей и пробелы будут отличаться).

### API-секрет

Используется тот же API Secret, что и для [webhook'ов комментариев](/guide-webhooks.html). Он привязан к паре (тенант, домен) и управляется в настройках API вашего тенанта. Если вы меняете секрет, вам следует заново развернуть верификатор, чтобы он читал новое значение до следующей доставки.

Когда платформа не находит **API-секрета** для совпавшего домена, доставка не происходит. В журнале webhook'ов фиксируется сбой с причиной "no API secret".

### Пример верификации (Node.js)

[inline-code-attrs-start title = 'Пример верификации подписи webhook'; type='javascript' inline-code-attrs-end]
[inline-code-start]
import crypto from 'crypto';

function verifyAgentWebhook(rawBody, signatureHeader, timestampHeader, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(`${timestampHeader}.${rawBody}`)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader),
  );
}
[inline-code-end]

Используйте `timingSafeEqual` вместо `===`, чтобы избежать утечки подписи через тайминг-каналы.

### Что находится в подписанном теле

Полный конверт плюс блок `data`, специфичный для события. См. [Полезные нагрузки Webhook](#webhook-payloads).

### Рекомендации

- **Проверяйте каждую доставку.** Если ваш эндпоинт принимает неподписанные запросы, у вас нет гарантии целостности.
- **Отклоняйте при несовпадении подписи.** Возвращайте 401 или 403; не отвечайте 200 OK при неверной подписи, иначе вы замаскируете атаки в журналах доставки.
- **Используйте HTTPS.** Подписи защищают целостность; TLS защищает конфиденциальность (как ваш секрет, так и текст комментария в полезной нагрузке).
- **Меняйте секреты**, когда уходят члены команды с доступом, или по расписанию.

### Защита от повторных атак

Само по себе подписывание не предотвращает replay-атаки — злоумышленник, перехвативший реальную подписанную доставку, может отправить её повторно. Защита от повторов — задача вашего эндпоинта:

- Используйте поле конверта `occurredAt` и отклоняйте доставки старше, скажем, 5 минут.
- Используйте `triggerId` или `approvalId` как ключ дедупликации — если вы уже обработали его, игнорируйте дубликат.
