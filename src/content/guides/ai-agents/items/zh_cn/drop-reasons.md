当某个触发器为某个代理触发但**未**导致 LLM 调用时，平台会记录一次带有原因的"丢弃"。丢弃会显示在[分析页面](#analytics-page)的"本月跳过的触发器"下方。

### 丢弃原因的完整列表

| 原因 | 发生了什么 |
|---|---|
| `agentDaily` | 达到了该代理的每日预算上限。 |
| `agentMonthly` | 达到了该代理的每月预算上限。 |
| `tenantDaily` | 达到了该租户的每日预算上限。 |
| `tenantMonthly` | 达到了该租户的每月预算上限。 |
| `qps` | 达到了该代理的每分钟速率限制（60 秒滚动窗口）。 |
| `concurrency` | 该代理的最大并发运行数已经饱和。 |

### 不在此列表中的情况

从未进入分发路径的触发器不会被"丢弃"并记录原因——它只是不会被分发。这包括：

- 代理处于**禁用**状态。
- 触发评论不匹配该代理的 [URL/语言区域范围](#scope-url-locale)。
- 触发操作是由同一个代理发起的（循环预防）。
- 租户的计费无效。
- 该代理不在租户的计划内。

这些是静默跳过，而不是丢弃。它们不会出现在分析页面的丢弃图表中。

### 在分析页面查看丢弃

[分析页面](#analytics-page)显示：

- **本月跳过的触发器** - 按丢弃原因分组的计数。
- **达到或接近上限的代理** - 按代理细分哪些代理正在推高上限，以及当前周期内被丢弃的触发器数量。

### 看到丢弃时该怎么做

- **`agentDaily` / `agentMonthly`** - 代理自身的上限设置得太紧。可以在编辑表单上提高上限，或者缩小代理的范围（URL/语言区域、更窄的触发器）。
- **`tenantDaily` / `tenantMonthly`** - 账户级别的上限设置得太紧。在租户计费设置中提高它，或者将支出分配到更少的代理上。
- **`qps`** - 流量达到了每分钟滚动窗口限制。这通常是病毒式传播的帖子产生触发器的速度快于代理运行速度的迹象。代理的 `maxTriggersPerMinute` 和 `maxConcurrent` 字段对此进行限制；提高它们会增加吞吐量，但也会增加突发成本。
- **`concurrency`** - 与 `qps` 的根本原因相同，但发生在进行中的运行数量上。如果需要更多并行度，请提高 `maxConcurrent`。

### 丢弃与错误

丢弃是"触发器从未运行"。**错误**是"触发器运行了，但 LLM 调用或工具分发失败"。错误在[运行历史](#run-history)页面（状态为 `Error`）单独跟踪。

### 丢弃也可能停止重放

相同的丢弃原因也会停止进行中的[测试运行/重放](#test-runs-replays)。重放会以 Error 状态停止，并显示一条消息，指明触发了哪个预算（例如，代理的每日预算）。

### 循环预防有意保持静默

对于"此触发器来自另一个代理，为防止循环而被跳过"这种情况，没有对应的丢弃原因。记录它只会让分析变得杂乱而没有有用的信号——按照设计，代理的扇出绝不应导致触发器爆炸。如果你怀疑某个本不该被抑制的循环被抑制了，请查看[评论日志](/guide-moderation.html#comment-logs)——机器人发布的评论上的 `botId` 是循环检查所依据的键。
