हर एजेंट वेबहुक को आपके टेनेंट के API सीक्रेट का उपयोग करके HMAC-SHA256 के साथ साइन किया जाता है। FastComments के कमेंट वेबहुक्स के लिए भी यही साइनिंग स्कीम उपयोग की जाती है - यदि आपने पहले से ही उन्हें इंटीग्रेट किया है, तो एजेंट वेबहुक्स उसी सिग्नेचर हेडर और सत्यापन प्रवाह का पुनः उपयोग करते हैं।

### साइनिंग क्यों

सिग्नेचर के बिना, जो हमलावर आपका वेबहुक URL जानता है, वह ऐसे नकली इवेंट POST कर सकता है जो FastComments से आए हुए प्रतीत होते हैं। साइनिंग का अर्थ है कि आपका एंडपॉइंट अपने कार्य करने से पहले सत्यापित कर सकता है कि हर डिलीवरी प्रामाणिक है।

### सिग्नेचर कैसे काम करते हैं

हर डिलीवरी के लिए:

1. प्लेटफ़ॉर्म टेनेंट + मैच किए गए डोमेन के लिए API सीक्रेट देखता है ([Webhooks Overview](#webhooks-overview) देखें)।
2. यह `X-FastComments-Timestamp` हेडर में वर्तमान Unix टाइमस्टैम्प (मिलीसेकंड में) भेजता है।
3. यह `HMAC-SHA256(api_secret, "${timestamp}.${raw_request_body}")` (Stripe-शैली) की गणना करता है और परिणाम को `X-FastComments-Signature` हेडर में `sha256=<hex>` के रूप में भेजता है।
4. आपका एंडपॉइंट टाइमस्टैम्प हेडर पढ़ता है, प्राप्त `${timestamp}.${body}` पर HMAC पुनः गणना करता है, सिग्नेचर हेडर में `sha256=<hex>` मान से तुलना करता है, और बेमेल होने पर अस्वीकार कर देता है।

साइन किया गया बॉडी वह **सटीक बाइट्स** है जो प्लेटफ़ॉर्म ने भेजा, जिसके आगे `${timestamp}.` लगा होता है - आपके सत्यापक को रॉ रिक्वेस्ट बॉडी का उपयोग करना चाहिए, पुनः सीरियलाइज़ की गई JSON स्ट्रिंग का नहीं (अन्यथा की ऑर्डरिंग और व्हाइटस्पेस में अंतर होगा)।

### API सीक्रेट

[कमेंट वेबहुक्स](/guide-webhooks.html) द्वारा उपयोग किया गया वही API Secret। यह प्रति (टेनेंट, डोमेन) होता है और आपके टेनेंट की API सेटिंग्स में प्रबंधित होता है। यदि आप सीक्रेट रोटेट करते हैं, तो अगली डिलीवरी से पहले नए मान को पढ़ने के लिए अपने सत्यापक को पुनः डिप्लॉय करें।

जब प्लेटफ़ॉर्म को मैच किए गए डोमेन के लिए **कोई API सीक्रेट नहीं** मिलता, तो डिलीवरी नहीं होती। वेबहुक लॉग "no API secret" कारण के साथ विफलता दर्ज करता है।

### सत्यापन उदाहरण (Node.js)

[inline-code-attrs-start title = 'वेबहुक सिग्नेचर सत्यापन उदाहरण'; type='javascript' inline-code-attrs-end]
[inline-code-start]
import crypto from 'crypto';

function verifyAgentWebhook(rawBody, signatureHeader, timestampHeader, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(`${timestampHeader}.${rawBody}`)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader),
  );
}
[inline-code-end]

सिग्नेचर के टाइमिंग-चैनल लीक से बचने के लिए `===` के बजाय `timingSafeEqual` का उपयोग करें।

### साइन किए गए बॉडी में क्या होता है

पूर्ण एनवेलप साथ ही इवेंट-विशिष्ट `data` ब्लॉक। [Webhook Payloads](#webhook-payloads) देखें।

### सिफ़ारिशें

- **हर डिलीवरी पर सत्यापित करें।** यदि आपका एंडपॉइंट बिना साइन वाली रिक्वेस्ट स्वीकार करता है, तो आपके पास कोई अखंडता गारंटी नहीं है।
- **सिग्नेचर बेमेल पर अस्वीकार करें।** 401 या 403 लौटाएं; खराब सिग्नेचर पर 200 OK न दें, अन्यथा आप अपनी डिलीवरी लॉग में हमलों को छिपा देंगे।
- **HTTPS का उपयोग करें।** सिग्नेचर अखंडता की रक्षा करते हैं; TLS गोपनीयता की रक्षा करता है (आपका सीक्रेट और पेलोड में कमेंट टेक्स्ट दोनों)।
- **सीक्रेट रोटेट करें** जब एक्सेस वाले टीम सदस्य जाएं, या निर्धारित अंतराल पर।

### रिप्ले सुरक्षा

केवल साइनिंग रिप्ले हमलों को नहीं रोकती - जो हमलावर एक वास्तविक साइन की गई डिलीवरी कैप्चर कर ले, वह उसे पुनः भेज सकता है। रिप्ले सुरक्षा आपके एंडपॉइंट पर निर्भर है:

- `occurredAt` एनवेलप फ़ील्ड का उपयोग करें और, मान लें, 5 मिनट से पुरानी डिलीवरी अस्वीकार करें।
- `triggerId` या `approvalId` को डिडुप की के रूप में उपयोग करें - यदि आपने पहले से ही उसे प्रोसेस किया है, तो डुप्लिकेट को अनदेखा करें।
